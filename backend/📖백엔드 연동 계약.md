# MVP 백엔드 연동 계약

- 작성일: 2026-09-29
- 최근 검증: 2026-09-30 (Cloud 문의·관리자·탈퇴 익명 계정 실측, 테스트 데이터 정리)
- 대상: `YH_3D_Game_MVP` C(YH) 백엔드 ↔ 팀 Godot/웹 클라이언트
- 상태: **본편 API 계약 초안 — 팀 확인·클라이언트 통합 전.** 계정·동기화, 주문/결제, 문의, 관리자, 탈퇴 Edge 함수 8개가 `Server 1`에 배포됐다. `support-chat` **v6 검증용 질문 2건**의 응답/DB 상태를 확인했다. Toss는 **가짜 결제 키로 승인 함수를 1회 호출해 서버 502·미지급**을 확인했다. **제공자 측 OpenAI/Toss 요청 로그·Toss 승인 성공·SDK/앱 결합·본편 게임 규칙 답변·이메일 연결/재설치 복구는 미검증**이며, 이 파일 전체를 최종 연동 완료 계약으로 전달하지 않는다.
- Cloud 대상: `Server 1`(ref `ecqfmaivywgzlbnqxymb`). 이전 PoC의 `poc_*` 테이블·함수·사용자·마이그레이션은 원격에서 삭제되었으며, PoC 폴더를 본편 배포에 사용하지 않는다.
- 근거: `DevelopDoc/PRD.md` 4.11~4.14, `TECH_SPEC.md` 7장·8.5, 사용자 확정인 APK 직접 배포·앱 내 Toss Android SDK·오프라인 플레이 후 동기화. 과거 `01_사전검증/백엔드/📖백엔드 연동 계약.md`는 역사적 자료로만 참조한다.

## 공통 경계

- 앱에 넣는 값: Supabase 프로젝트 URL·**공개** publishable 키. Supabase Auth 세션의 사용자 access token으로 로그인 호출을 인증한다. 서비스 역할 키, Toss 테스트 시크릿 키, OpenAI 키는 앱·웹·로그·Git에 넣지 않는다.
- 서버는 요청 JSON의 `user_id`, `role`, `amount`를 권한 증거로 믿지 않는다. 검증한 사용자 JWT와 서버 가격표·주문을 정본으로 사용한다. 인증 없는 함수 호출은 거부한다.
- 정상 함수 요청은 `POST` + JSON; 오류 응답은 가능하면 `{ "error": "오류_코드" }`. Supabase 게이트웨이의 인증 오류 형식은 함수 자체의 오류와 다를 수 있으므로 HTTP 상태와 JSON 본문을 함께 확인한다.
- 게임 플레이는 오프라인에도 계속된다. 서버 로그인이 안 되는 첫 실행은 **기기 안의 임시 게스트**로 기록하고, 연결 후 익명 로그인에 성공하면 같은 이벤트 ID를 서버로 전송한다. 로그인·결제·문의는 온라인 전용이며, 네트워크 실패 시 outbox를 보존한다.
- 클라이언트 구현·SDK 콜백·화면·공동 Godot 파일의 팀 소유자는 아직 미정이다. C는 이 서버 계약과 서버 구현을 맡으며 앱 코드를 임의 수정하지 않는다.

## 계정과 복구

| 흐름 | 계약 및 완료 조건 |
|---|---|
| 게스트 | 온라인 `signInAnonymously()` → 동일 세션 재실행 유지 → `ensure-profile` 요청. 오프라인 첫 실행은 로컬 임시 게스트로 시작 |
| 프로필 | `POST /functions/v1/ensure-profile` 요청 `{}` → `{ "profile": { "user_id": "<Auth UUID>", "nickname": "", "is_guest": true, "role": "user" } }`. 서버가 JWT 사용자 ID로 생성/조회하며 역할을 초기화해 덮어쓰지 않음 |
| 이메일 연결 | Cloud Manual Linking 허용 → 현재 익명 세션에서 `updateUser({ email })` → 이메일 확인 → `updateUser({ password })`. **같은 사용자 ID**·기록/구매 유지 실측 필요. 이메일과 비밀번호를 한 번에 설정하는 가짜 계약 금지 |
| 재설치·다른 기기 | `signInWithPassword({ email, password })` 후 본인 진행·인벤토리 재조회. 동기화되지 않은 로컬 대기 기록은 복구 대상이 아님 |
| 비밀번호 재설정 | `resetPasswordForEmail()`로 메일 발송 → Android 복귀 링크에서 유효한 복구 세션 확인 → `updateUser({ password })`. 복귀 URL·메일 실수신은 앱 담당과 별도 실측 필요 |
| 로그아웃 | 세션 삭제 후 새 게스트로 시작. 기존 영구 계정의 서버 기록은 보존 |
| 닉네임 | `profiles.nickname`은 본인만 변경 가능. `role`, `is_guest`, 다른 사용자 ID는 클라이언트가 수정 불가 |
| 회원 탈퇴 | `POST /functions/v1/delete-account` 요청 `{ "confirm": true }`. 서버가 **본인 JWT만** 사용해 Auth 계정 삭제 → `200 { "status": "deleted" }`. 2026-09-30 Cloud에서 위조 `user_id`를 무시하고 본인 익명 계정/문의 행만 삭제, 다른 계정 보존을 재조회했다. 구매·진행 기록이 존재하는 영구 계정의 전수 삭제와 앱의 로컬 기록/세션 정리는 미검증 |

## 오프라인 진행 동기화

- 단말 outbox 이벤트: `{ "id": "<생성 시 고정한 고유 ID>", "kind": "mission|distance", "payload": { ... } }`. B의 미션 ID·스테이지·거리 이벤트 세부 규격은 팀과 맞춰야 한다. 이벤트 ID는 재시도 시 바꾸지 않는다.
- `POST /functions/v1/sync-progress` 요청 `{ "events": [ ... ] }`(1~100건 목표) → 목표 `200 { "received": 2, "inserted": 2 }`. 같은 계정·같은 ID 재전송은 `inserted: 0`; 다른 계정은 자기 이벤트만 읽는다. 실패·타임아웃·거부 응답에서는 outbox를 지우지 않는다.
- 복구 읽기 목표: `GET /rest/v1/sync_events?select=client_event_id,kind,payload,created_at&order=created_at.asc`, `GET /rest/v1/mission_progress?select=stage_id,mission_id,completed_at`. RLS로 본인만 읽고, 앱이 재로그인 후 복원한다. 구매 효과는 게임 진행 이벤트로 생성하거나 지급하지 않는다.
- 실검증 기준: 두 사용자 교차 조회·쓰기 차단, 동일 ID 재전송 1회 반영, 오프라인→연결→이메일 연결→재설치 복구. **과거 PoC의 부분 통과를 본편 검증으로 재사용하지 않는다.**

## 테스트 주문·승인과 지급

| 단계 | 요청·응답 목표 |
|---|---|
| 주문 | `POST /functions/v1/create-toss-order` `{ "product_id": "ammo_start_pack" }` → `201 { "orderId": "<서버 생성 ID>", "productId": "ammo_start_pack", "amount": 1100, "orderName": "시작 탄약 팩", "status": "ready" }`. 임의 `amount`를 요청에 넣으면 거부. 상품 가격은 서버 기준 |
| 앱 인증 | Godot Android 플러그인이 **앱 내 Toss Android SDK UI**를 열고 서버의 `orderId`·금액을 전달. SDK 성공/실패/취소와 성공 시 `paymentKey`·`orderId`·`amount`를 서비스 어댑터에 전달하는 경로는 **팀 클라이언트 담당 구현·실기기 검증 필요** |
| 서버 승인 | `POST /functions/v1/confirm-toss-payment` `{ "paymentKey": "<SDK 인증 결과>", "orderId": "<주문 ID>", "amount": 1100 }`. 본인 주문·서버 금액 일치 확인 → 서버에서 Toss **테스트 승인 API** 호출 → 단일 DB 거래로 구매·인벤토리·주문 paid 반영. 목표 성공 `200 { "status": "paid", "orderId": "<같은 ID>" }` |
| 중복·취소 | 동일 결제 결과 재전송은 **추가 지급 없이** `already_paid`; 타인 주문·변조 금액은 거부. 앱 성공 화면만으로 지급하지 않고 `toss_orders.status`·`inventory`를 서버에서 재조회. SDK 취소/실패·승인 실패는 미지급 |
| 웹(F-111) | 기존 P0를 임의 삭제하지 않음. 웹은 별도 UI이되 같은 서버 주문/승인 계약 사용. 웹 구현·배포 소유자는 팀 결정 전 |

Toss 테스트 키와 유효한 실제 테스트 인증 결과가 없는 동안에는 **승인 성공·중복 지급 검증 완료라고 쓰지 않는다**. 카드사·은행 앱 인증으로 일시적 앱 전환은 가능하지만 외부 시스템 브라우저는 앱 주 결제 UI가 아니다.

## 문의·제보와 관리자

- `POST /functions/v1/support-chat`: 질문 `{ "kind": "question", "message": "탄약은 어디서 얻나요?" }`, 버그 제보 `{ "kind": "bug", "message": "진행이 멈췄어요", "bug_context": { "app_version": "0.1.0", "last_run": {} } }`.
- 응답 `{ "threadId": "<UUID>", "status": "ai_answered|needs_human", "reply": "<답변 또는 팀 전달 안내>" }`. 프론트는 HTTP `200`/`202` 단독이 아닌 **본문 `status`**로 화면을 분기한다. 버그 제보·합성 사용량 30회 제한을 Cloud에서 확인했고, 2026-09-30 사용자 승인 아래 최신 **v6 검증용 질문 2건**에서 고유 문구 답변과 모르는 게임 질문의 `needs_human` 상태·DB 기록을 확인했다. `functions/_shared/게임_안내_테스트.ts`의 문구는 **실제 게임 사실이 아니다.** 배포 v3→v6의 소스 변경 여부와 제공자 측 API 사용량은 독립 확인 전이며, 실제 본편 규칙 답변·결제/환불 분류의 Cloud 동작은 미검증이다.
- 관리자 목록은 `POST /functions/v1/admin-overview`의 `{ "section": "members" }` → `200 { "section": "members", "items": [...] }`로 조회한다(`section`: `members`, `purchases`, `support` 중 하나). 서버가 JWT 사용자 ID로 `profiles.role='admin'`을 확인한 뒤 서버 역할로 지정된 세 뷰만 조회하며 목록은 **최대 100행**이다(페이지 넘김 미구현). 회원 이메일은 `email_masked`만 노출하며 실제 주소의 마스킹/이메일 연결은 아직 실측 전이다. 앱 일반 사용자의 API 호출 `403`, 뷰 직접 SELECT 거부를 Cloud에서 확인했다.
- 팀 답변은 `POST /functions/v1/admin-support-reply`의 `{ "threadId": "<UUID>", "reply": "<답변>", "status": "closed" }` → `200 { "threadId": "<같은 ID>", "status": "closed" }`이다(`status`: `in_progress`, `closed` 중 하나). 서버는 JWT 관리자 ID를 전달하고 DB `admin_reply`도 역할을 다시 확인한다. 2026-09-30 Cloud에서 일반 사용자 답변 거부, 팀 답변·스레드 상태 변경·본인 조회를 확인했다. 사용 안내 초안은 `../docs/ADMIN_GUIDE.md`. **Supabase Studio 프로젝트 멤버 권한은 앱 `profiles.role`과 별개**이며 Studio UI 실사용 검증은 아직 아니다.

| 범위 | 현재 상태 |

| 제공자 비밀 설정·노출 점검 | 후속 읽기 전용 조회에서 **`TOSS_TEST_SECRET_KEY`**·`OPENAI_API_KEY`·`OPENAI_MODEL` 세 이름의 등록을 확인했으나 값·모델 ID·토스 키 세트 매칭은 노출/검증하지 않았다. 앞서 잘못 안내한 `TOSS_SECRET_KEY`는 코드가 읽지 않는다. 지정 키 형식은 마지막 검사 당시 코드·문서 106개와 로컬 Git 이력 10개 커밋 텍스트 패치에서 0건; `.env.example`만 추적. APK/웹 빌드·로그·실제 `.env` 내용은 검사 범위 밖 |
| 앱·웹 연결 | 팀 클라이언트 소유자·공동 파일 경계·SDK 결과 전달을 아직 합의하지 않음 |

요청·응답의 목표 예시는 **구현 완료의 증거가 아니다**. 필드나 상태가 달라지면 같은 계약 파일을 수정하고 클라이언트 담당에게 변경점을 알린다. Git 커밋·머지·푸시와 **새 범위의** `Server 1` 원격 적용·비밀 키 등록은 각각 별도 승인 전까지 하지 않는다.
